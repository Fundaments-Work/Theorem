# Release

### Versioning & Stability Convention

- **Stable Releases**: Only `X.Y.0` versions (e.g. `1.0.0`, `1.1.0`, `1.2.0`, `1.3.0`, `1.4.0`, `1.5.0`) are designated as **stable** production releases.
- **Beta / Pre-releases**: All minor/patch versions (`X.Y.Z` where `Z > 0`, e.g. `1.5.1`, `1.5.2`, `1.5.3`, etc.) are designated as **beta / pre-release** versions.
- Whenever releasing or editing any `X.Y.Z` (`Z > 0`) tag on GitHub, always ensure it is marked as a pre-release:
  ```bash
  gh release edit v<version> --prerelease
  ```

### Before tagging a release

1. **Merge branches into `main` first**:
   Always merge feature/fix branches into `main` before tagging. Releases and documentation builds depend on commits being present on the `main` branch.

2. **Run full local quality gates**: every step of [Quality Gates](../AGENTS.md#quality-gates-before-every-commit), including `pnpm foliate:check`, Android clippy and `pnpm e2e`.

3. **Bump version in all 5 files**:
   - `package.json` — `version` field
   - `src-tauri/Cargo.toml` — `version` field
   - `src-tauri/tauri.conf.json` — `version` field
   - `src-tauri/crates/theorem-sync-core/Cargo.toml` — `version` field
   - `src-tauri/crates/theorem-core/Cargo.toml` — `version` field

4. **Update `CHANGELOG.md`** with the new version, release date, and detailed change entries.

5. **Regenerate icons** from `public/favicon.svg` (the source used by CI):
   ```bash
   pnpm tauri icon public/favicon.svg
   ```

6. **Landing page automated rebuild hook**:
   - Theorem landing page (`theorem-landing`) auto-rebuilds via `.github/workflows/notify-landing.yml` upon release publication using repository secret `CLOUDFLARE_DEPLOY_HOOK_URL`.
   - The Hugo build parses `CHANGELOG.md` directly from `main` and updates `https://theorem.fundaments.work/changelog/`.

7. **Tag and push**:
   ```bash
   git tag v<version>
   git push origin v<version>
   ```
   CI (`release.yml`) triggers on tags matching `v[0-9]+.*`, builds all targets (Linux, macOS Intel & Apple Silicon, Windows, Android), signs artifacts, and publishes to GitHub Releases.
   If the release is a minor/patch version (`X.Y.Z` where `Z > 0`), mark it as a pre-release in GitHub:
   ```bash
   gh release edit v<version> --prerelease
   ```

### Release CI troubleshooting

The release workflow publishes a **draft** release first, then flips it public only if every platform job succeeds. So a failed job leaves assets uploaded but the release unpublished — fix and re-run rather than rebuilding from scratch.

**Android builds fail intermittently with a Maven Central `403`** (seen on 1.5.9):
```
Could not GET 'https://repo.maven.apache.org/maven2/org/jetbrains/kotlin/kotlin-stdlib/...'
Received status code 403 from server: Forbidden
> A problem occurred configuring project ':buildSrc'
```
This is Gradle failing to download the Kotlin plugin — a network/upstream issue, **not** a code defect. Re-run the failed job and it will pass:
```bash
gh run rerun <run-id> --failed
```
Do not "fix" this in the Rust code. To confirm the Rust side is genuinely healthy for Android before re-running:
```bash
cd src-tauri && cargo clippy --target aarch64-linux-android
```
Notes for debugging: Android logs are only downloadable **after** the whole run completes (`gh run view --job <id> --log-failed`), and the real Gradle cause sits *above* the verbose `Io(...)` wrapper error — search the log for `What went wrong`. Job IDs via `gh run view <run-id> --json jobs --jq '.jobs[].databaseId'`. Android takes ~20 min; Windows is usually the long pole.

### Android adaptive icon

The Android icon files in `src-tauri/gen/android/` are normally
auto-generated by `tauri android init` with Tauri defaults and then
ignored by `.gitignore`. Our customizations to these files must be
committed via the gitignore exceptions at `.gitignore:46-57`.

After running `tauri android init --ci`, CI regenerates these files
from the template. The `pnpm tauri icon public/favicon.svg` command
regenerates platform PNGs but does NOT regenerate the vector drawables
in `drawable-v24/`. These XML files are our permanent customization.


### Screenshot assets

Before publication, refresh and visually review the screenshots with the private
`fundaments-agent-harness` workflow in `screenshots/README.md`. Its capture script
uses isolated demo data; its export script updates this repo and
`theorem-landing` locally. It does not deploy either repository.

`Screenshots/README.md` is the placement guide and contact-sheet index.
`Screenshots/manifest.json` records the app revision, viewport sizes, public book
editions, feed URLs and dictionary attribution. Phone assets are responsive
browser captures; use native device captures for system bars or native dialogs.
Keep source captures and the full-resolution ZIP in harness state rather than
committing duplicate archives or book files.

Automatic CI runs on pushes to `main`, once when the same commit is pushed to
both maintained branches. PRs targeting either branch and manual CI runs remain
available. Check dependency updates locally or manually on `1.6.1` before
integration. Dependabot version PRs remain active. Publishing still requires
the maintainer’s approval of the release/tag step.

### Workflow selection and shared builds

`scripts/ci-changes.sh` selects web, Rust, Android and E2E checks by changed paths.
A main push compares against the last successful main CI run rather than the
immediately preceding commit: cancelling an older run cannot drop its unchecked
changes. PRs compare against their base; manual runs, an unavailable baseline or
an API failure select every gate. Documentation-only changes skip build jobs.
Nightly runs select only the frontend/native build needed for full E2E, skipping
the daytime unit/lint and Android jobs.
Run `node --test scripts/ci-changes.test.mjs scripts/release-tag.test.mjs scripts/check-release-assets.test.mjs e2e/lib/specs.test.mjs e2e/lib/webdriver.test.mjs` to verify
selection, cancellation coverage, unavailable baselines, release-tag checkout,
prerelease classification and request timeouts.
A selected workflow-check job runs these selection tests and pinned actionlint
and ShellCheck when workflows, local actions or the selector change.
Local actionlint validation must have ShellCheck on PATH (or pass its path with
`-shellcheck`) to match the hosted check. Validate locally with
`actionlint` (v1.7.12) or `go run github.com/rhysd/actionlint/cmd/actionlint@v1.7.12`.

The web job uploads one verified `dist` artifact. The Rust job restores it for
all-feature linting and builds the E2E executable using the same Cargo cache as
the normal Rust checks. It strips copies of the executable and tauri-driver for
transfer; the E2E runner restores executable permissions and installs runtime
packages, without another Rust or frontend build. E2E remains non-blocking and
its hosted WebKit screenshot failures remain visible; artifact reuse does not
skip assertions. Relevant main pushes use the launch/import/reader smoke suite;
full coverage runs nightly at 21:17 UTC or through the manual `e2e_suite: full`
choice. Manual CI defaults to smoke, while local `pnpm e2e` remains full. PRs do
not add native E2E builds. Frontend/E2E-only changes can build the native E2E app
without rerunning unrelated Rust tests. The smoke/full policy is documented in
`docs/testing-e2e.md`; full local E2E is required before release.

Release and manual dry-run workflows use the same composite frontend actions.
One Linux job checks the Foliate runtime, builds/verifies the frontend, generates
platform icons, and uploads both. All native platform jobs restore that artifact
and use `src-tauri/tauri.ci.conf.json` to bypass the already completed frontend
hook. Normal local builds retain `pnpm build`. Native jobs still install frozen
frontend dependencies for the Tauri CLI and bundled resources; pnpm and Cargo
caches reduce those installs. The Vite production build has no target-platform
conditional, so these assets are shared across platforms.

Release reruns resolve the existing requested tag to an immutable commit, use
that revision for release notes and every platform build, and serialize attempts
for the same tag without cancelling signing/uploads. Only `X.Y.0` without a
suffix is stable; all patch releases are prereleases. Dry runs are manual only
and do not need extra `release-check/*` branches. Dry runs remove cached bundle
outputs before building and require every installer/signature pattern through
`scripts/check-release-assets.sh`. Patterns stay literal until expansion inside
the bundle directory; unquoted patterns with `nullglob` previously vanished
before the check loop, allowing missing signatures to pass. The shared-action workflows
must exist at the selected tag; tags predating these actions need their original
workflow. No workflow optimization itself grants permission to tag or publish.

CodeQL keeps its weekly/manual scans and dependency/workflow-triggered main
scans. It analyzes JavaScript/TypeScript, Rust, Actions and the Homebrew Ruby
formula; the empty Python analysis job is removed. Documentation pushes dispatch
only the studio docs refresh. Releases and manual notification requests also
refresh the product landing page, through one shared notification action. The
release workflow calls it explicitly because releases published using
`GITHUB_TOKEN` do not trigger another workflow ([GitHub event rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)).
