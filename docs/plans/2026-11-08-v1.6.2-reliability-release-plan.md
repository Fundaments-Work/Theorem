# 1.6.2 reliability prerelease plan

Status: planning. Work on `main`; `1.6.2` is a prerelease. Scope and
verification results must be updated as work lands. No release date is set.

## Goal and scope

Fix confirmed issues, integrate ready contributions, and deliver a release
whose artifacts can be traced to the tested revision. The 1.6.1 public desktop
assets were not confirmed to match its rebuilt tag; verify 1.6.2 independently
without modifying the existing release. The detailed process and restrictions
remain in [the release runbook](../release.md).

## Work queue

- [ ] Establish the baseline: compare `main` with `v1.6.1`, inspect current
  CI and open PRs, and record relevant outstanding failures and release risks.
- [ ] Investigate [#181](https://github.com/Fundaments-Work/Theorem/issues/181)
  and [PR #182](https://github.com/Fundaments-Work/Theorem/pull/182). Reproduce
  in the real app, explain why Sonner's normal action dismissal is insufficient,
  and verify the fix at a layer that observes the notification and navigation.
  Review the contributor's changes, documentation, changelog and checks.
- [ ] Investigate [#180](https://github.com/Fundaments-Work/Theorem/issues/180):
  map the existing import stages, native progress and Android job lifetime;
  design a first slice with truthful stage/byte progress and visible errors.
  Verify navigation, unknown sizes, cancellation and mixed results on the
  relevant platforms. Include the panel only when safely implemented and tested.
  Native Android foreground queue and durable recovery are a separate slice;
  include them only if implemented and physically verified in time. Keep #180
  open until all of its acceptance criteria are met.
- [ ] Review dependency PRs [#178](https://github.com/Fundaments-Work/Theorem/pull/178)
  and [#179](https://github.com/Fundaments-Work/Theorem/pull/179), including
  compatibility, lockfiles and relevant checks.
- [ ] Review a PR for [#154](https://github.com/Fundaments-Work/Theorem/issues/154)
  if submitted. Include it only if review and verification are complete; it is
  not a release blocker. Record platform and real-app testing limitations.
- [ ] Validate reading rhythm and onboarding with readers: observe the setup,
  first-book and resume tasks, and record completion and usability feedback.
  Test Android interaction on a physical device. With participants' consent,
  follow weekly goals over several weeks and compare qualifying reading days
  and reported usefulness with their own baseline using local summaries or
  volunteered exports; do not add telemetry by default. Treat novelty and
  participant differences as limits, and version any changes to reward rules.
  Record what was actually studied and leave unfinished follow-up explicit.

## Release preparation

- [ ] Update behavior documentation and unreleased changelog as changes land.
- [ ] Set the version in the five files listed in the release runbook, date the
  changelog at publication, regenerate icons and review resulting changes.
- [ ] Review and refresh screenshots as required by the release runbook.
- [ ] Run all quality gates, Foliate reproduction, both Android clippy targets,
  and the full native E2E suite on the exact final release commit. Record
  commands, results and any physical-device coverage separately.
- [ ] Review the final commit, CI, release notes and outstanding risks with the
  maintainer. Obtain approval for integration where required and separately
  for the tag and publication.
- [ ] After approval, tag `v1.6.2` from the verified commit on `main`; verify
  platform artifacts, signatures and updater manifests, and confirm the published
  release is marked prerelease. Follow the runbook if a build or draft fails.

## Decisions and results

The release is focused on reliability and issue fixes. The import progress
slice and incoming read-along contribution are conditional on readiness; the
complete Android recovery feature is not assumed to be ready. No gates,
device tests, merges, tag or publication have been completed under this plan.
